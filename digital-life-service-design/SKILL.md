# 数字生命服务设计（Digital Life Service Design）

## 范式转移

旧范式 = 固态流水线（需求 → 开发 → 测试 → 部署）：部署即终点，代码是资产，开发者是建造者。（**这是简化对照，不是史实**：真实团队早就在做迭代开发与运维反馈。此处的"固态"指默认假设，不是说以前没人迭代。）

新范式 = 栽培活体：上线即起点，数据 + 外化技能是资产，开发者是育种师。

公式：**行业解决方案 = Seed（种子）+ Harness（挂载）+ Memory（演化）**

核心转移：只把"确定的那部分"固化成种子，其余交给环境与数据持续演化。

## 三器官

- **Seed（种子）**：底层规则与行业基因（SOP、知识本体、合规边界、价值观护栏）。
  是"出厂设定"，也是个性化起点。同一颗种子在不同土壤（用户场景）长成不同助手。
- **Harness（挂载）**：感官与神经系统。**注意同词异义**：本处指环境接入能力；Agent 运行时外壳（控制循环/上下文/预算/恢复）是另一个东西，见 `harness-design`。
  - 观察力：屏幕视觉感知、传感器接入，像人一样"看"界面、跨系统抓信息。
  - 执行力：标准化 Agent 与软件对话、自动化操作、API 编排、零侵入集成现有系统。
  让通用模型瞬间与行业场景对齐，把 Agent 从"缸中之脑"解放出来。
- **Memory（演化）**：外化经验，如树木年轮。向量库记录历史/偏好/教训，Action-Observation 反馈回路，据此修正执行脚本。上线不是终点而是起点。
  **但"写回"不等于"生效"**：经验先落为候选，经离线回放 → 实验 → 批准才发布为策略。字段、撤销与失效传播见 `retention-diagnosis-loop` 的"共同账本"。缺这一步，Memory 会变成旧经验长期支配新任务。

## 设计原则

1. **只写不变，不写全部**：Seed 锁死必要条件（哪些关系破坏价值必崩），充分路径留给演化。**谁有权改种子**见 `seed-extraction` 的"变更权"——那是提示层约束，真正的强制要沉到权限层。
2. **环境自动对齐**：Harness 主动连接现实，不被动等输入，打破数据孤岛。**验收必须具体**：接入能力 ≠ 任务理解正确。可判定的验收 = 在目标系统上完成 N 个真实任务的端到端成功率 + 权限越界次数为 0。只写"能连上"不算对齐。
3. **上线即起点**：Memory 闭环持续演化，而非交付即终点。
4. **价值判据转移**：从"拥有功能"转向"拥有高质量行业私有数据 + 高效外化技能"。**"高质量 / 高效"目前无度量，这是方向判断而非验收标准**：资产质量不能替代用户结果，最终仍以价值层的真实改变为准（见 `retention-diagnosis-loop` 的三角验证）。
5. **端侧优先隐私**：明文不出设备，服务端只存密文/脱敏特征/聚合指标；私钥在设备，服务器只有公钥。
   验收：服务器泄露时，攻击者无法还原"谁在何时说了什么、处于什么状态"。

## 商业闭环（也是生命的一部分）

- 投流获客 = Harness 的触角（伸向真实用户获取反馈的执行能力）。
- 渠道/素材效果 = Memory 记录的经验。
- CAC ≤ 1/3 LTV = 可配置经营参数（**不是核心种子**，随生命周期调整）。

铁律：**真实用户价值 → 留存 → LTV → 商业可持续**，单向因果链，不能倒灌。
经营层是价值的下游，不是价值的替身。为了商业牺牲价值 = 空心增长。

## 角色终局

从"建造者"到"育种师"，只做三件事：编写行业种子、搭建 Harness 环境、守护进化方向。

系统能自动跑"运营 + 微调"；**不能**自动跑"守方向 + 改种子"。
价值指向与评价基因，永远是人在闭环之外握着的方向盘。
