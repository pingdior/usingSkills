# Agent 设计技能行为回归

本目录提供可复用的设计响应场景与评分要求。cases.json 中的 expected 和 hard_failures 供评审者使用，不应随提示泄露给执行模型。
这些是场景规格，不是已完成的模型实验，也不是生产运行时的副作用测试。

## 两层检查

本地检查器验证五个入口的基本元数据、内部 Markdown 引用、机制编号和场景规格完整性。
它不证明指导内容正确、模型会遵守、外部写入幂等或统计方法适合真实数据。

~~~bash
python3 scripts/check_agent_design_skills.py
python3 -m unittest discover -s tests/agent_design -v
~~~

## 行为评测方法

1. 固定模型、宿主指令、工具能力、任务预算和原始材料，记录模型与仓库提交版本。
2. 执行模型只接收案例 prompt、setup 指定的环境和所需技能；expected / hard_failures 留给评审者。
3. 按目标安装方式测试实际技能发现；显式选技能的测试与自动路由测试分开记录。
4. 同一场景分别运行基线与修订版；每次使用新会话，不透露原评审结论。按模型随机性和成本选择重复次数，并记录，不把单次结果当稳定结论。
5. 按可观察行为评分，不按措辞、标题、固定问题数或固定轮数。
6. 保留未参与修改的新场景验证泛化；仅有此处案例通过不能宣称整体提升。

对于 standalone-skill，只提供指定目录，确保引用的 sibling 契约不可读取；否则无法测试降级行为。
案例里的数字、合同和操作均为给定场景，不是外部事实。所有写入相关案例仅要求设计方案；如果要验证实际副作用，需要另建隔离模拟器和执行记录，不得调用真实订单或通知服务。

## 记录结果

每次保存：case_id、model / runtime、skill_commit、可用技能和工具、输入、响应或 trace、每项行为观察、硬失败、token、时延及未完成原因。
若需要用户多轮回答，使用预先一致的回答材料，分别记录必要追问和无谓追问；不要为了让某版通过而改变用户答案。

expected 的各项分别标记满足、部分满足、未满足或无法观察，并说明证据。
任何 hard_failure 命中都应独立报告，不能被总分平均掩盖。
报告应区分「模型给出了正确恢复方案」与「模拟系统实际未重复写入」。

没有运行模型时，只能报告规格与一致性检查结果，不能填行为通过率或效果提升百分比。
